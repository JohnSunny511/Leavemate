Leave Management System – Project Documentation
Technology: ASP.NET Core MVC · C# · ADO.NET · SQL Server · Stored Procedures

Phase 1 – Database Creation (Database First)
1. Created SQL Server database LeaveManagementDB.
2. Created four tables:
   - Employee – Employee details (ID, Name, Age, Email, Department).
   - Admin – Admin details (ID, Name, Email).
   - Login – Login credentials (ID, reg_id, username, password, role).
   - Leave – Leave applications and approval details.
3. No foreign key or CHECK constraints created inside the table definitions.
4. Created stored procedures:
   - sp_EmployeeRegister – Employee registration.
   - sp_AdminRegister – Admin registration.
   - sp_Login – Verifies username and password, returns reg_id and role.
   - sp_EmployeeDashboard – Employee dashboard statistics.
   - sp_AdminDashboard – Admin dashboard statistics.
   - sp_ApplyLeave – Inserts leave application and checks overlapping dates.
   - sp_MyLeaves – Retrieves employee leave history.
   - sp_AllLeaves – Retrieves all leave applications with status filtering.
   - sp_UpdateLeaveStatus – Approves/rejects leave and saves admin remark.
5. Tested stored procedures directly in SSMS.
6. Modified Employee table to include emp_age.
7. Changed Login table's email column to username.

Design Decisions and Implementation Changes
1. Changed ID Passing from TempData to Route Parameters
Initially, the project used TempData to pass the logged-in user's ID and role between pages.

The earlier approach was:
TempData["reg_id"] = id;
TempData["role"] = objcls.role;


Subsequent controller actions retrieved the ID using:
int id = Convert.ToInt32(TempData["reg_id"]);


However, the project was changed to follow the trainer's method of passing IDs through route parameters.

New approach:

After successful login, the stored procedure returns reg_id and role.

The controller redirects the user to the appropriate dashboard:
return RedirectToAction(
    "DashboardLoad",
    "Employee",
    new { id = user.reg_id }
);


The dashboard receives the ID directly:
public IActionResult DashboardLoad(int id)
{
    Employee obj = dbobj.DashboardDB(id);
    return View(obj);
}


In Razor views, IDs are passed through navigation links:
<a asp-controller="Employee"
   asp-action="MyLeavesLoad"
   asp-route-id="@Model.emp_id">
    My Leaves
</a>


Why this change was made:
- Makes the ID-passing process easier to understand.
- IDs are visible in the URL.
- No need to retrieve IDs from TempData on every page.
- Makes navigation between pages straightforward.
- Follows the method demonstrated by the trainer.
2. Stored Procedure Returns Both ID and Role During Login
Instead of asking the user to select Employee or Admin during login, sp_Login retrieves the role automatically.

This avoids requiring the user to remember or select their account type.

The returned role determines which dashboard the user is redirected to.
3. Controller Organization Based on Features and Roles
The project follows a feature-based and role-based controller structure rather than creating a separate controller for every database table.
- AccountController – Registration, Login and Logout.
- EmployeeController – Employee registration, dashboard, Apply Leave, My Leaves and Profile.
- AdminController – Admin registration, dashboard, Manage Leaves and Profile.
A separate LeaveController is not required because applying for and viewing leave applications are employee-related features.
